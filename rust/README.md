# Obsidian Predictor — отдельная утилита (Rust)

Перенос [`obi_predict.py`](https://github.com/EQUENOS-2/Obsidian-Predictor/blob/main/src/obi_predict.py) из
[EQUENOS-2/Obsidian-Predictor](https://github.com/EQUENOS-2/Obsidian-Predictor) на Rust. Оригинальная утилита и логика
предсказания принадлежат EQUENOS.

Работает так же, как оригинал: на входе litematic, на выходе файл вейпоинтов Xaero. Только в несколько сот раз
быстрее. Реальный скан 2116×280×1023 (606 млн блоков) считается за 2,9 с вместо примерно 20 минут. Алгоритм не
менялся, подробности в разделе [Отличия от Python-версии](#отличия-от-python-версии).

Утилита нужна там, где мод поставить нельзя, а litematic сделать можно, например на сервере без мода. Сам мод из
этого репозитория делает то же самое прямо в игре и без litematic.

## Сборка

Нужен [Rust](https://rustup.rs). В этой папке:

```sh
cargo build --release
```

Программа появится в `target/release/obsidian-predictor` (на Windows — `obsidian-predictor.exe`). Собирать нужно на
той же системе, где будете запускать.

## Как пользоваться

1. Сохраните периметр в Litematica как схематику. В конце имени файла через пробел укажите координаты `Corner 1`,
   например `Terrain Scan 42 -64 42.litematic`. Можно и не указывать, тогда программа спросит их сама.
2. Запустите программу одним из способов:
   - двойным щелчком, откроется окно выбора файла;
   - перетащив `.litematic` на программу;
   - из терминала:

   ```sh
   obsidian-predictor "Terrain Scan 42 -64 42.litematic"
   obsidian-predictor scan.litematic 42 -64 42      # Corner 1 явно
   ```

3. В текущей папке появится `<имя> waypoints.txt`. Скопируйте строки в нужный файл вейпоинтов Xaero, как с
   оригинальной утилитой.

Вейпоинты значат то же, что в оригинале:
- **красные** — лаву нужно закрыть или осушить; вейпоинт на поверхности лавового озера значит, что закрыть нужно все
  поверхностные источники в радиусе как минимум 20 блоков;
- **чёрные** — взрывоустойчивые блоки, по одному вейпоинту на связную группу.

## Отличия от Python-версии

В нескольких местах Python-версия берёт «первый» элемент из `set`. Какой элемент окажется первым, решает внутреннее
устройство CPython, а не алгоритм. Здесь, как и в моде, в этих местах используется порядок добавления. От этого
зависит, на какой блок лавовой зоны или группы взрывоустойчивых блоков встанет вейпоинт, а в больших лавовых озёрах
иногда и сколько будет красных вейпоинтов. Какие зоны лавы затапливаются и какие группы находятся — совпадает
полностью.

Сравнение с Python-версией на шести реальных сканах местности (от 7 до 606 млн блоков):

- с Python-кодом, где `set` заменены на множества с порядком добавления, результат совпадает побайтово;
- оригинальная Python-версия находит на каждом слое ту же затопленную лаву и те же взрывоустойчивые блоки;
- вейпоинты, которые сдвигаются, обычно сдвигаются на 1–2 блока и никогда не выходят за свою зону или группу.

## Тесты

```sh
cargo test --release
```

`tests/reference.rs` запускает программу на схематиках из `../src/test/resources/predictor/` и сравнивает результат
с эталонным выводом Python, который лежит там же. Java-тесты мода используют те же файлы.

### Сверка с Python-версией

Если `obi_predict.py` изменится, перенесите изменение сюда и в мод, затем сверьте. Скриптам нужен Python с `numpy`
и `nbtlib`, а также копия оригинального репозитория:

```sh
export OBSIDIAN_PREDICTOR_SRC=/путь/к/Obsidian-Predictor/src
python parity/ref_run.py orig    scan.litematic out/orig    0 0 0   # оригинальный Python
python parity/ref_run.py ordered scan.litematic out/ordered 0 0 0   # Python с упорядоченными set
target/release/obsidian-predictor scan.litematic 0 0 0              # должно побайтово совпасть с out/ordered
python parity/compare.py out/orig out/ordered                       # те же зоны и группы, отличается только выбор точек
```
